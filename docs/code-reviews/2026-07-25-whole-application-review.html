Scope and completeness contract

The review cannot be declared complete until every row in the file ledger has an explicit terminal status, every finding has a disposition, and all feasible verification checks have a recorded result. New first-party files discovered or created during the work must be added to the ledger and reviewed too.

Auditable first-party scope

  • Package.resolved, an ignored but locally present dependency lockfile used by the build.
  • This living report, archived as docs/code-reviews/2026-07-25-whole-application-review.html.
  • docs/code-reviews/README.md, the durable index and naming convention for future reviews.
  • Tests/LoopTuneAppTests/CredentialStoreTests.swift, added during the review to cover credential-account isolation and URL sanitization.
  • Any other first-party file added or changed while fixing findings.

Recorded non-source trees

These trees are not silently skipped. They are classified by provenance and verified at the boundary appropriate to their role:

  • references/: 4,181 local files / 679 MB of cloned prior-art repositories, research notes, and fixtures; intentionally Git-ignored and not part of the application. Boundary check: confirm the package, products, scripts, and tests do not compile, bundle, execute, or otherwise depend on mutable files from this tree.
  • .build/: baseline snapshot 9,819 local files / 935 MB of SwiftPM-generated dependency checkouts, intermediates, and binaries; regenerated during final verification. These are not authored source. Boundary check: regenerate via clean dependency resolution/build/test, verify the pinned dependencies, and inspect emitted warnings/errors rather than treating object files as reviewable source.
  • .git/: repository metadata, excluded from application behavior. Boundary check: record branch, worktree state, tracked-file inventory, and final diff.

Review method

Every first-party file receives a deliberate read. AI-generated code is treated as untrusted: names, comments, tests, and apparently standard formulas are checked against actual behavior rather than accepted as evidence of correctness.

Test growth is intentionally uncapped. Missing behavior, boundary, malformed-input, safety, time-zone, unit, calculation, and recommendation coverage will be added as focused regression, table-driven, golden-reference, or property-style tests. Tests must be capable of detecting a plausible implementation error; agreement between an AI-written test and AI-written production code is not sufficient evidence by itself.

Correctness

Inputs, outputs, invariants, off-by-one boundaries, rounding, optionals, error paths, and state transitions.

Safety

Medical guardrails, unit conversions, time zones/DST, stale or incomplete data, unsafe defaults, and failure visibility.

Concurrency

Swift 6 isolation, cancellation, task lifetime, shared mutable state, UI-thread work, and deterministic ordering.

Security & privacy

Credential storage and redaction, URL/token handling, TLS assumptions, persistence, cache isolation, and sensitive logging.

Resilience

Malformed Nightscout payloads, partial responses, pagination, redirects, network errors, corrupt cache/history, and recovery.

Product behavior

CLI contracts, SwiftUI flows, accessibility, diagnostics, progress/cancellation, export, documentation, packaging, and CI.

Finding severity

  • Critical: credible risk of materially unsafe medical output, credential exposure, or destructive loss.
  • High: core workflow is wrong or fails for ordinary valid input; major security/privacy defect.
  • Medium: edge-case correctness, reliability, or UX defect with meaningful impact.
  • Low: maintainability, documentation, accessibility, or minor behavior issue.

Findings register

F-001 · High · Insulin-affecting overrides are discarded before tuning

Fixed + verified

TreatmentIngest builds OverridePeriod values, but TuningPipeline.fetchInputs drops them and TuningInputs has no override field. Glucose behavior during a 70%/120% insulin-needs override is therefore attributed to the ordinary basal, ISF, and carb ratio. The design document explicitly says these intervals should be excluded.

Resolution: Overrides now flow through TuningInputs, exclude replay samples and affected carb records, and report the excluded count in UI, text, JSON, and persistence. Regression coverage proves both selective exclusion and refusal when every usable sample is excluded.

F-002 · High · Settings changes take effect only at the next 04:00 tuning boundary

Fixed + verified

ChainedTuner checks profile history only at the start of each 04:00-to-04:00 window. A change at noon can replay and tune the following 16 hours with the old profile. The existing “mid-window” test checks eventual detection, not application at the actual timestamp.

Resolution: Tuning and diagnostics now split at exact therapy-change timestamps, including changes within a one-day analysis. Target-only uploads are deliberately ignored so they do not fragment replay. Tests cover noon changes, one-day changes, and non-therapy uploads.

F-003 · High · Selected insulin type is not applied to historical profiles

Fixed + verified

The configured insulin model is added to the current profile only. Multi-day chaining immediately replaces that profile with an entry from ProfileHistory, whose insulin type remains nil. Doses without their own insulinType can therefore use the wrong/default effect curve.

Resolution: The configured insulin model is applied to every historical profile that lacks an explicit model, while preserving explicit per-profile and per-dose values. Dedicated history tests verify both behaviors.

F-004 · High · A run can succeed with no usable samples

Fixed + verified

The pipeline checks only that two glucose records exist anywhere in the supplied input. Records can all be outside the analysis window or separated by unusable gaps; chained tuning then returns an unchanged “recommendation” with zero samples instead of failing visibly.

Resolution: The public offline path validates its window and physiological values, limits glucose evidence to that window, and requires at least 12 usable post-exclusion deviation samples. Clear errors replace plausible-looking zero-evidence recommendations.

F-005 · High · Untuned-hour smoothing can bypass pump-relative basal caps

Fixed + verified

BasalTuner applies caps and then smooths untouched hours using the uncapped historical profile. When historical and current profiles differ, smoothing can move a value back outside the promised 0.7×–1.2× current-pump range.

Resolution: Basal values are capped again after smoothing, and evidence counts are assigned to the prior hours actually adjusted by a deviation. A regression test uses divergent historical/current rates to prove all final values stay inside pump-relative caps.

F-006 · High · A token can be sent to a different host; remote HTTP is accepted

Fixed + verified

Editing the URL does not clear or reload the token field, so a token restored for site A can be transmitted to site B. The client also accepts non-loopback http:// URLs, exposing query-token or API-secret credentials and medical data in transit.

Resolution: URL changes reload or clear credentials for the normalized host and port; saved URLs strip paths, queries, fragments, and pasted tokens. Non-HTTPS transport is rejected except for loopback development hosts. App and client tests cover port isolation, sanitization, host switching, and remote HTTP rejection.

F-007 · Medium · Non-five-minute CGM intervals are treated as five-minute deviations

Fixed + verified

Intervals up to 20 minutes are accepted, but observed, insulin, and carb deltas are not normalized to the five-minute units assumed by categorization thresholds and tuning formulas. A 15-minute rise can be counted at roughly three times the intended magnitude.

Resolution: Accepted 5–20 minute intervals now normalize observed glucose change, insulin effect, carb effect, and average delta to five-minute equivalents before categorization. An irregular-interval regression test verifies the scale.

F-008 · Medium · Malformed profile/treatment data can default silently, disappear, or trap

Fixed + verified

Examples include a missing schedule value becoming zero, invalid units/time zones becoming mg/dL/UTC, out-of-range finite doubles trapping during integer conversion, non-finite doses passing ingestion, and lenient array decoding dropping records without telling the caller. For a medical-analysis input boundary these conditions need validation and visible failure.

Resolution: DTO and ingest validation now rejects non-finite, overflowing, nonphysical, unknown-unit, invalid-timezone, malformed-schedule, and malformed-history inputs. Element-wise decoding still identifies corrupt records but the client fails the request with the skipped count instead of silently tuning incomplete evidence.

F-009 · Medium · Diagnostics overstate what the in-sample replay proves

Fixed + verified

The UI calls a fit against the same historical data “more accurate,” which reads like outcome validation. If the recommendation makes mean deviation materially worse, the message incorrectly says it “barely changes the fit.” Diagnostics also ignore override exclusions and historical profiles.

Resolution: The UI now labels this explicitly as an in-sample historical fit, reports worsening honestly, carries the medical disclaimer, excludes override intervals, and replays “before” against the profile recorded as active for each segment rather than the current profile.

F-010 · Medium · Dependency resolution is not reproducible from a clean clone

Fixed + verified

Package.resolved exists locally but is ignored. ArgumentParser is declared with a version range, so a clean checkout or CI run may build different dependency code than the reviewed revision.

Resolution: Package.resolved is no longer ignored, ArgumentParser is exact-pinned to 1.8.2, and LoopAlgorithm remains pinned to revision 2f5c630084aa0d72b8d14999e1e0f7c836b0c341. A clean resolve/build/test used those values.

F-011 · Medium · Machine-readable recommendations omit the medical disclaimer

Fixed + verified

The text report includes the mandatory warning, but --json does not. This contradicts the implementation plan’s “disclaimer everywhere output is produced” requirement and is especially risky because JSON is the format most likely to be forwarded or automated.

Resolution: Recommendation JSON now includes the same mandatory disclaimer plus days tuned and override-exclusion context. Unit tests and the live CLI mock assert the warning is present in machine-readable output.

F-012 · Medium · Boundary deduplication fingerprints omit medically relevant fields

Fixed + verified

Treatment deduplication ignores delivered amount, absolute rate, override factor/range, reason, automatic status, and stable Nightscout identifiers. Distinct reconciled records can collide, while the DTO currently throws away _id/syncIdentifier.

Resolution: Nightscout stable identifiers are retained and preferred. When absent, a deterministic sorted-key encoding of every decoded treatment field is used. Tests prove that boundary copies deduplicate while same-time records with distinct delivered amounts survive.

F-013 · Medium · Persisted-data APIs accept unsafe IDs and hide failures

Fixed + verified

RunStore constructs paths directly from a public run ID, allowing traversal outside the run directory, and negative limits can form invalid slices. Save/Keychain errors are ignored, so the UI can claim a run or credential was persisted when it was not.

Resolution: Run IDs and cache day keys use strict filename validation, limits clamp safely, and health-data directories/files use owner-only 0700/0600 permissions. Save, delete, and Keychain operations return success and produce a visible UI notice when persistence fails.

F-014 · Low · The active sidebar omits the planned warning and failed runs hide history

Fixed + verified

The unused ConnectionForm has a disclaimer, but the actual SidebarView does not. After any failed analysis, DetailPane prioritizes the failure forever, so selecting an existing saved run cannot reopen it.

Resolution: The active sidebar displays the medical warning and notices. Detail selection now takes precedence over the most recent failure, so saved runs remain accessible after an unsuccessful analysis.

F-015 · Low · Project documentation contains stale and contradictory status claims

Fixed + verified

PLAN.md simultaneously marks chaining/charts/Keychain work pending and completed, labels a nonexistent CLI report subcommand as done, and several test titles claim behavior their assertions do not prove.

Resolution: README and PLAN now match the implemented commands, exact settings segmentation, override behavior, evidence minimum, security model, dependency pins, and test suite. The DST test was renamed and strengthened to assert the nonexistent-time result it claims.

Disposition summary

15 confirmed findings were fixed and regression-tested: 6 High, 7 Medium, and 2 Low. No finding is open or deferred. No Critical issue was identified.

Residual validation limits

  • This is an engineering code review and historical-model test suite, not clinical validation or medical advice.
  • The final integration used a deterministic local Nightscout mock; no private real-world account or personal dataset was available to the reviewer.
  • The native app received a launch/liveness smoke check and its state logic was reviewed and tested, but no fully automated macOS click-through was available.
  • Golden oref0 parity independently anchors basal and ISF math. Carb-ratio behavior has focused sign, bounds, empty-data, and integration tests but no external clinical oracle.
